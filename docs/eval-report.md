## 2. 评测方法

### 2.1 用例结构

30 条，5 类各 6 条，其中 **12 条是负样本**（6 条该调工具、6 条该拒答）。文件：`data/eval/eval-set.tsv`（9 列）。

| 列 | 作用 |
|---|---|
| `expect_source` | 期望命中的文档类型（POLICY / CATEGORY / REALTIME / -） |
| `answer_keywords` | 答案必须包含的要点，`;` 分隔表示「全部命中」，`\|` 表示同义词任一命中 |
| `expect_contains` | 更强的唯一断言（B 类填商品 ID），仅用于检索层 |
| `should_call_tool` | 1 = 期望调用工具 |
| `should_refuse` | 1 = 期望拒答 |

### 2.2 判定规则

| 类别 | 主断言 | 辅助断言 |
|---|---|---|
| A/B/C | 答案含全部关键词组 | 命中片段的 `docId` 属于期望来源 |
| B | 检索片段包含商品 ID | 关键词 |
| C | 同 A + 是否调工具 | |
| D | `tool_call_log` 按 `sessionId` 有记录 | 答案不出现「没有相关资料」 |
| E | 答案含拒答表达（12 种） | 不允许编造 |

判定脚本：`tools/run_eval.py`（纯标准库，无需 pip）。用例校验：`tools/check_eval_set.py`。

## 4. 三个关键发现

### 4.1 RAG 召回差，不是阈值问题，是 topK 截断

现象：政策类问题（A01「退货要提供什么凭证」）的 top5 **全是休闲鞋商品片段**（0.69 分），政策片段一条都没有。

把候选池开大后（`k=20`，即 fetch=40，阈值 0.40）：

| 用例 | 池里 POLICY 条数 | POLICY 最高分 | CATEGORY 最高分 |
|---|---|---|---|
| A01 退货凭证 | **8 条** | **0.7613** | 0.6989 |
| C03 换货保修期 | **15 条** | **0.8146** | 0.6928 |
| C05 屏幕保修 | 4 条 | 0.7528 | 0.7867 |
| C01 500内休闲鞋能退吗 | **0 条** | none | 0.7975 |

**政策片段分数比商品更高，却进不了 top5**。根因：RediSearch 的 KNN 是「先取 K 个最近邻，再应用 similarityThreshold 过滤」；商品语料 341 块、政策只有 21 块，密度差 16 倍，前 K 名被商品占满。

**修复**：`ai.rag.fetch-multiplier` 从 2 提到 8（候选池 10 → 40）。效果：

```
A01 修复前 top5：5 条休闲鞋商品（0.69）
A01 修复后 top5：5 条政策片段（0.7613 / 0.7453 / 0.7430 / 0.7273 / 0.7065）
```

A 类 **5/6 → 6/6**。代价：`costMs` 从约 1.9s 涨到 2.4s。

### 4.2 阈值 0.68 的来历（以及 0.4 为什么等于不过滤）

Spring AI 的 `RedisVectorStore.similarityScore()` 做了一层换算：

```java
score = (2.0f - 余弦距离) / 2.0f;   // 即 1 - 距离/2
```

所以 `score = 0.5` 对应「余弦相似度 0（正交）」，`score = 0.4` 对应余弦相似度 **-0.2** —— 原来的 0.4 连噪声都放行。

实测底噪：无关问题（「今天深圳天气」）也能召回 5 条，分数 **0.66~0.67**。扫描 8 档（k=5）：

| 阈值 | 召回命中 | 空召回 | 噪声放行 |
|---|---|---|---|
| 0.62 | 9/18 | 0 | 6 |
| 0.65 | 9/18 | 0 | 6 |
| 0.66 | 9/18 | 1 | 5 |
| 0.67 | 9/18 | 1 | 5 |
| **0.68** | 9/18 | 2 | 4 |
| 0.69 | 9/18 | **6** | 1 |
| 0.70 | 9/18 | **8** | 0 |
| 0.72 | 9/18 | **8** | 0 |

两条结论：
1. **召回命中在所有阈值下恒为 9/18** —— 阈值不改变召回，只改变「误杀 / 噪声」。那 9 条失败是 topK 截断导致的（见 4.1）。
2. 0.69 起空召回从 2 跳到 6，开始把能答的问题打成「没有相关资料」。**0.68 是拐点前一档**。

### 4.3 评测脚本本身的 5 个测量缺陷

原始脚本报 33%，逐行对照后端协议后发现 20 个"失败"里 12 个是测量问题：

| 缺陷 | 表现 | 正确做法 |
|---|---|---|
| 用 SSE 帧字段判断工具调用 | `'tool_calls' in data` 恒为 False（后端只发 delta/done/error） | 从 done 帧取 `sessionId` → 查 `tool_call_log` |
| 商品 ID 断言作用在回答文本 | 模型不会把内部 ID 念给用户 → 必然失败 | 断言作用在**检索片段** |
| 来源断言依赖不存在的 `source` 字段 | 条件永久跳过，看着在测其实没测 | 用命中片段的 `docId` |
| 拒答只认「无法/不支持」 | 「抱歉…没办法推荐电影」被判失败 | 12 种表达 或 行为判定 |
| 关键词无同义变体 | 「七日」对不上「7日」 | `7日\|七日` |

**教训**：评测结果不可信时，先检查评测脚本，别急着改系统。

| 用例 | 问题 | 失败原因 | 归类 |
|---|---|---|---|
| C01 | 500以内的休闲鞋能七天无理由退吗 | 只召回商品片段，缺「7日/折旧费」 | 检索：商品语言挤占政策 |
| C02 | 拉杆箱退货的物流费谁承担 | 只召回拉杆箱商品，缺「物流费」 | 同上 |
| C05 | 手机屏幕碎了算保修范围吗 | 只召回手机商品，缺「非保修/付费」 | 同上 |
| C06 | 我买的手机还没发货能退吗 | 未调订单工具（回答只要政策） | 期望争议：可判「应索要订单号」 |

**前 3 条是同一个根因**：问题里带「休闲鞋/拉杆箱/手机/屏幕」等商品词，向量更贴近商品目录，即使候选池开到 40 条，政策片段也排不进前 5。

## 7. 已知限制

| # | 限制 | 影响 | 解法 |
|---|---|---|---|
| 1 | **混合意图检索不平衡** | C 类 33% | 查询分解（拆成商品子问题 + 政策子问题分别检索）或按来源分路检索 |
| 2 | **商品粒度粗** | 无法稳定精确到单个 SKU | 按商品切分（chunk≈250 字）并重建索引 |
| 3 | **无登录体系** | 订单查询未校验归属（`GET /orders/{id}` 是内部接口） | 接入 JWT 后在 `OrderTool` 里校验 `order.userId` |
| 4 | **单库混合检索** | 大语料淹没小语料（341 vs 21） | 引入 BM25+向量的混合检索，或按 source 分索引 |
| 5 | **样本量 30** | 波动 ±2 条 | 扩到 100 条；或用固定 seed + temperature=0 |
| 6 | **工具轮次无代码上限** | 仅靠提示词约束「最多调一次」 | 自己实现工具循环并限制 maxRounds |
